# Swipe Deck and mental-model scoring (8.6)

**What it is.** Laya decides which mental models to offer an agent, from all 99, using only the index (each model's name and its one-line "when to use"; she never reads a whole note). Everything that happens with a model is judged with a heart or a skull, so the memory system keeps improving: Menu > Panels > Swipe Deck.

**How Laya picks (the funnel, `thinking.py`, job 6).** Two steps so it stays fast: (1) Laya scores the 8 families (a family's name plus a few of its models' names); (2) she scores every model in the best `families_top` (2) families, plus `explore` (2) models from the other families so none is frozen out, and the top three above the confidence threshold are offered. Hearts and skulls nudge the scores (a model by 0.75x to 1.25x once it has 3 points; a family by the average of its models' factors). Nobody's hand-picked list narrows the pick, and every agent gets the same funnel. On the VM a pick takes 9 to 11 seconds (6 to 7 batches of about 1.7 s; Laya serves one job at a time). `families_top = 1` would be faster and narrower.

**The friend's hand-picked lists are scrapped (2026-11-11, the owner's call).** Laya picks from all 99 models through the funnel, so nothing needs a shortlist. The `mental_models` field was removed from every template manifest, and `config/mental_model_lists.json`, `integrations/subagents/fill_mental_models.py`, the ledger's shortlist code and the `mental_models.lists` setting were deleted. They are all in git history if they are ever wanted.

**Three kinds of card** (`xiar_hermes/swipe_deck.py`, files `~/.local/state/xiar/swipe-deck/picks.jsonl`, `votes.jsonl`, `skips.jsonl`, `judges.json`):
1. **Laya's pick**: the models Laya offered the agent for a task (the funnel above). Up to three.
2. **Agent's pick**: the ONE model the agent actually opened with `xiar_mental_model` to make its decision (plugin `tool_mental_model`).
3. **Outcome**: what came of it. At the agent's next turn its previous answer (first 300 characters) is kept as an outcome card for the model it used. If the owner corrects the agent right after, the latest card gets an automatic skull.

**Points** (the owner's rule): owner 3, cloud bot 2, bigger local bot 2, agent 1 (its own choice = a heart for the model it used), Laya 1 (its own pick = a heart for the models it offered), auto 1 (a correction = a skull). Every card counts the same; the points are the weights.

**Who judges is the owner's setting** (Judges in the panel). The owner may vote or leave everything to the bots. The cloud bot is off until the owner picks a connection; the local bot is on by default (the local model that runs here, so nothing leaves the machine); each can be turned off. A bot that is on goes through EVERY waiting card by itself (when a card is made, when switched on, and every minute from the Settings bridge, panel open or not). **A card stays in the deck until every switched-on judge has voted, then it moves to the history. Nothing is ever deleted.** A bot that cannot answer a card twice is marked skipped for it, so no card waits forever.

**Blind judging.** A bot sees only: the task excerpt (160 characters), the picked model(s) with their note (trimmed: 650 characters each for Laya's pick, 1,500 for the agent's pick, 1,100 for an outcome) and, for an outcome card, the first lines of the agent's answer (300 characters). Never the owner's vote, private memory or files. The ledger refuses a bot vote once the owner has voted, so the owner sees a card only after the switched-on bots have judged it, and their opinions stay sealed until the owner votes (then the panel shows what each said, and +5 XP for each agreement). A cloud connection sends that text to its provider: the owner's choice, and the panel says so. Calls go through the vetted adapter (`integrations/model-connections/call.py`); a local connection behind managed auth gets its bearer the way the model router does it (never read by hand, never printed).

**Ranking.** A model's rank is a smoothed share of weighted hearts. It nudges Laya's score 0.75x to 1.25x, only once 3 points are behind the model. It never decides anything alone.

**The panel** (`GUI/src/settings-web/SwipeDeckView.tsx`, route `/panels/swipe-deck`, view id `swipe-deck`, so "open Swipe Deck" works in chat). A full-screen page laid out like Galaxy's Swipe Deck: no holo panel and no holo table. Left: title, combo / hearts / skulls / level and XP, the daily quests and streak, the Judges settings and the log. Right: the card to swipe (drag right for a heart, left for a skull; the heart and skull buttons and the arrow keys do the same), with two rings behind it. Behind both, standing where the holo table was: ONE glass brain, the one from the VR XIAR memory graph (`GUI/public/models/glass-brain.glb`, a copy of `crates/memory/assets/brain_mesh_source.glb` ; there it is `SM_BrainMesh` with the `M_CelestialGlass` material), drawn as glass (a bright rim, a faint body) and turning slowly with the table's gentle float. The mesh is already upright (y up, x front to back, the hemispheres split along z). The 99 models are dots inside it, a cluster per family with the family's name beside it, placed the way that memory graph places its notes: a hub per family spread across the mesh's own vertices (farthest-point sampling), the dots jittered around it and kept inside the shape (green glow = loved, red = skulled, bigger = more votes), each dot bobbing slightly. If the model file cannot be loaded, a brain built in code stands in. Click any model on a card, in the log, or in the arena to read its note in a modal (Escape closes). Bridge commands (`integrations/settings-panel/swipe_deck.py`): `swipe_state`, `swipe_vote`, `swipe_note`, `swipe_judges`, `swipe_judges_set` (write tier), `swipe_judge_now`.

**Daily quests and streak** (`Deck.stats()`, the machine's local days): "Judge 5 cards", "Agree with a bot 3 times", "Clear the deck" (at least one vote today and nothing waiting). Each finished quest adds 20 XP (`QUEST_XP`). The streak counts days in a row with at least one vote from the owner, ending today (or yesterday while today has none yet); the best run is kept.

**Laya's picks failing on the VM.** Job 6 had 16 successful and 20 failed picks in the log. One batch takes about 1.7 s on the VM CPU and Laya serves one job at a time, so the shared 5 s timeout failed whenever Laya was busy. Job 6 now waits up to `mental_models.laya_timeout_s` (20 s) per batch, retries a batch once, and the log says why a pick failed (`error`). The other Laya jobs keep the 5 s default.

**Not built yet.** Positive automatic signals beyond the agent's and Laya's own points (task finished, checks passed). The live path "Laya makes a pick, the agent opens a model, the next turn makes an outcome card" is covered by unit tests and a direct run of the scoring on the VM, not yet watched on a real agent turn.
